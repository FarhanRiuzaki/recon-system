# API contract

What the API answers: `apps/api`, Bun + Elysia + Drizzle on PostgreSQL, one module per area under
`apps/api/src/modules/`. The browser calls `/api/x` on the Next server; Next forwards it to the API at `/v1/x` (same
path below `/v1`, same method, query and body), so every `/api/...` path in this document is also the API's `/v1/...`
path. The source of truth is the zod schemas in `packages/shared/src/contracts/*`, which the web and the API both
import; `schemas/` holds one JSON Schema (draft 2020-12) per schema, generated by `bun run api:schemas`
(`apps/web/scripts/emit-api-schemas.ts`, zod's `z.toJSONSchema`). Do not edit `schemas/` by hand:
`apps/web/src/test/api-contract.test.ts` fails when the files differ from the zod source, and
`apps/api/test/architecture/conformance.test.ts` fails when the endpoint table below misses a route of the API or lists
one it doesn't serve.

Request schemas (`…Body`, `…Query`, `BulkUserFilter`) describe what the client sends: a field with a `default` may be left out. Every
other schema describes the answer exactly (`additionalProperties: false`).

## Category selections and saved views

List category parameters accept legacy scalar values and repeated singular keys: users `role`/`status`, projects
`status`, permissions `module`, activity `action`, and sign-in log `event`/`method`. For example,
`/api/projects?status=active&status=archived` selects either status. Values within a group use OR; groups, search
and time conditions use AND. An absent/empty scalar or empty JSON body array leaves that group unrestricted.
Arrays allow at most **50 raw elements before exact deduplication**; empty elements, unknown enum choices, nested
or non-string body elements and larger arrays are 400. List query validation still runs before the session guard.
Unknown well-formed role/action strings return no matches. Query values are literal: commas and JSON-looking role
names are never split/coerced. Other query keys retain the first-value rule. Canonical URLs dedupe and sort choices
by codepoint; CSV/count and users bulk `filter` use the same full-dataset predicates as the list. Bulk command
`assignRole.role` stays scalar; permissions, actor rank and bulk/export caps are unchanged.

Named saved views keep the complete query up to **4096 characters**. Navigation preferences keep their existing
300-character per-page cap: longer current queries clear the prior remembered view and explain the fallback;
the URL continues to work and may be saved as a named view. Overlong named views are refused without truncation.

## Time filters

Dashboard and both audit GET endpoints accept either an inclusive calendar pair `from` / `to` (YYYY-MM-DD, at most 92 days), or a precise `start` / `end` pair (at most 366 days). The two forms cannot be mixed. Precise windows include start and exclude end. Endpoints are ISO timestamps with an explicit zone, `now`, or restricted date math (`now-15m`, `now-1M`, `now/d`, `now/w+1w`). Units are seconds `s`, minutes `m`, hours `h`, days `d`, weeks `w`, months `M` and years `y`. Rounding uses the app time zone; weeks begin on Monday. Each request resolves both endpoints against one clock. JSON pages and CSV exports apply identical filters. Dashboard day buckets aggregate only matching events; its period includes resolved start/end timestamps.

## Rules for every endpoint

- The browser calls only same-origin `/api/*` on the Next server. The backend is reached from Next server code
  through `API_BASE_URL` (server env); its address never reaches the browser.
- Answers are JSON with `Cache-Control: no-store`, except the CSV export and the OAuth redirects and landing page.
- Errors: `{ "error": { "code": string, "message": string } }` ([ApiErrorBody](schemas/ApiErrorBody.json)). The
  message is UI copy (English, says what happened and what to do); unknown failures are 500 `internal` with a fixed
  message, never the thrown text.
- Error codes and statuses are fixed: `unauthenticated` 401, `forbidden` 403, `csrf` 403, `not_found` 404,
  `bad_request` 400, `duplicate` 409, `rate_limited` 429, `invalid_credentials` 401, `account_inactive` 403,
  `invalid_code` 400, `superadmin_locked` 409, `last_superadmin` 409, `self_action` 409, `role_in_use` 409,
  `ldap_password` 409, `already_enabled` 409, `only_sign_in_method` 409, `last_space_admin` 409, `space_archived` 409,
  `self_approval` 409, `invalid_state` 409, `day_closed` 409, `password_change_required` 403, `internal` 500.
- A user whose password an admin set (Create user with a password, Reset password; `mustChangePassword` on
  [UserDto](schemas/UserDto.json)) gets 403 `password_change_required` on every route but GET `/api/auth/context`, GET
  `/api/me`, GET `/api/spaces`, POST `/api/me/password` and sign-out, after the 401 and before any permission check, until they set
  their own (POST `/api/me/password`, or a reset link).
  One code is sent with another status on purpose: `invalid_credentials` is 400 when a signed-in user's current
  password is wrong (`PATCH /api/me`, `/api/me/password`, `/api/me/reauth`, `DELETE /api/me/2fa`), so the browser
  doesn't take it for an ended session.
- Check order in every guarded handler: parse the body or query (400) → session, CSRF, permission (401/403) →
  existence (404) → rules (403/409) → change → activity entry. A query is checked before the session (the GET rows
  below); a body's 400 comes right after the guard. `apps/api/test/architecture/conformance.test.ts` fails when a handler
  answers 404 before its body check.
- 429 answers send `Retry-After` in seconds.

### Sessions, CSRF, same origin

- The session is the `sk_session` cookie (sealed, `httpOnly`, `SameSite=Strict`, `Secure` when `COOKIE_SECURE=true`).
  It holds only the session id, the CSRF token and the pending-2FA marker; permissions are computed per request from
  the user's current roles, so a role change or a deactivation applies on the next request.
- Guarded endpoints (every row below with a permission or "signed in") check in this order: no live session → 401
  `unauthenticated`; a POST/PATCH/PUT/DELETE without the session's token in `x-csrf-token` (constant-time compare)
  → 403 `csrf`; missing permission → 403 `forbidden`, before any data is read. The signed-in layout hands the token to
  the browser.
- `/api/auth/*` POSTs carry no CSRF token (there is no session yet) but must be same-origin: `Sec-Fetch-Site:
  same-origin` (or `none`), or an `Origin` equal to the site's public origin (`APP_URL`); otherwise 403 `forbidden`. Sign out with a
  full session needs `x-csrf-token` too.
- Credential sign-in defaults to `method: "auto"`: email, username or NIP resolves the registered account, then only its provider can authorize it. Explicit `password` and `ldap` remain supported. Failed automatic proofs run one argon2 verification plus one directory check when configured; successful local proofs do not depend on directory availability. The input badge is a format hint (numeric NIP → LDAP), not an account lookup.
- A sign-in that passed the password step of a 2FA account holds only the pending marker (10 minutes): every guarded
  endpoint answers it 401; it can only finish (`/api/auth/2fa`) or cancel (`/api/auth/logout`).
- A session ends `SESSION_TTL_HOURS` (default 12) after sign-in (`expiresAt`, absolute) or after
  `SESSION_IDLE_MINUTES` (default 120) without a request, whichever comes first. The next request with it answers
  401 and the record is deleted; lists and counts of sessions (`/api/me/sessions`, `/api/users/{id}/sessions`, the
  dashboard) drop ended ones first. Any request (API, page load, server prefetch) marks the session seen, but
  `lastSeenAt` is written at most once a minute, so it is accurate to a minute and idle time to a minute too.
- Changing a credential or the sign-in identity needs the current one again (re-authentication): the password change,
  turning 2FA off, and a new email on `PATCH /api/me` (`currentPassword`; the directory password for LDAP users).
  Wrong answers share the backoff below. An account that signs in only through Google or Apple keeps the provider's
  email (409 `self_action`), can't turn 2FA on (the provider checks it, so a code would never be asked; 400), and turns
  2FA off with a recovery code instead of a password.
- Connecting Google or Apple adds a way to sign in, so it needs a session that proved the user within the last 10
  minutes (`MeDto.reauthFresh`): a sign-in counts, and so does `POST /api/me/reauth` (the password, the directory
  password for LDAP users, or a recovery code for an account without a password). Otherwise the link start is 403
  `forbidden` and the browser lands on `/me/security?oauth=reauth`. An account with neither a password nor 2FA has no
  second proof: it signs in again (400 `bad_request` from `/api/me/reauth`).
- A password change ends the user's other sessions and spends their open reset and invitation links; an admin reset
  and a reset by link end all of their sessions.
- Sign-in steps (`login`, `2fa`) are limited per client IP (10 per minute), fleet-wide (300 per minute) and per
  username (5 per minute), with a soft backoff per username after 3 failures (1 s, 2 s, 4 s … up to 60 s, cleared
  after 15 quiet minutes or a success). A signed-in user's wrong current password or recovery code (`PATCH /api/me`,
  `/api/me/password`, `/api/me/reauth`, `DELETE /api/me/2fa`) backs off after 5 failures (one budget per user).
- A per-client-IP limit applies only when the web knows the client IP (`TRUSTED_PROXY=true` behind a proxy that sets
  `X-Forwarded-For`); without it every IP is "unknown" and the per-IP limits are skipped, the others still apply.
- `POST /api/auth/forgot` is limited per client IP (10 per minute), per email (3 per 15 minutes) and fleet-wide (300
  per minute, without `TRUSTED_PROXY` too). A throttled request still answers 200 `{ ok: true }` and sends nothing,
  so the limit reveals nothing about which emails exist.
- Every limiter and backoff is a PostgreSQL row (`rate_limits`, `login_backoff`, UNLOGGED tables) updated by one atomic
  upsert per attempt, so the limits hold across API processes; the janitor deletes rows that no longer count.

### Sign-in log

- Events: `login_success` (a sign-in without a second factor, OAuth included), `password_ok` (the password step of a
  2FA account passed; the code is still due), `2fa_success`, `2fa_failed`, `login_failed`, `logout`, and
  `password_reset` (a new password set through a reset or invitation link). A completed sign-in is `login_success` or
  `2fa_success`; the dashboard counts only those.
- `login` is the account's email whenever the attempt matched an account (typed as username or email), otherwise the
  text that was typed. `userId` is null for an unknown login. A Google/Apple attempt logs `method` = the provider;
  for an identity that isn't connected to a user, `login` is the provider's email (else its subject).

### Lists (paging)

- Query: `page` 1–1000 (default 1; deeper is 400, narrow the filters instead), `pageSize` 15, 25, 50 or 100 (default
  15), `q` up to 200 characters (lists that search), `sort` = `key` or `-key` from the endpoint's own list (the enum in
  its `…Query` schema), plus the endpoint's filters. A value outside these is 400 `bad_request`, checked before the
  session. Query values arrive as strings: `page` and `pageSize` are parsed as numbers (`?page=2`), so the JSON
  Schemas give their input type as a string of digits or a number; anything else is 400.
- Answer: `{ items, total, page, pageSize, totalCapped? }` (the `…Page` schemas). `totalCapped: true` means counting
  stopped at `total` (the UI shows "N+"). A page past the end answers empty `items` with the real `total`. No list
  answers an unbounded array.
- Bulk answers: `{ done: string[], skipped: { id, code }[] }` ([BulkResult](schemas/BulkResult.json)); a protected
  row is skipped with its error code, the rest are applied, and only `done` rows reach the activity log.

### Rules a JSON Schema can't carry

- [ActivityQuery](schemas/ActivityQuery.json), [AuthLogQuery](schemas/AuthLogQuery.json): `from` and `to` come as a
  pair of calendar dates in the app time zone (both days included), `to` ≥ `from`, at most 92 days apart.
  `format=csv` answers `text/csv` (attachment) with the whole filtered list, newest first, up to 10,000 rows; a cell
  that starts with `=`, `+`, `-`, `@`, tab or CR (after optional spaces) gets a leading `'`.
- [CreateUserBody](schemas/CreateUserBody.json): a directory (LDAP) user has neither `password` nor `invite`; any
  other user has exactly one of them; `invite` needs `isActive` true (an inactive user gets a password instead).
- [UpdateRoleBody](schemas/UpdateRoleBody.json): `add` and `remove` apply to the role's current permissions and may
  not share a name. Nothing to change → 200 with the role, no activity entry.
- [CreatePermissionsBody](schemas/CreatePermissionsBody.json): the part before the dot is a module of the catalog
  (`packages/shared/src/permissions.ts`); the catalog holds at most 500 names (more is 400). Superadmin holds an added
  name at once; any role can then be given it (`PATCH /api/roles/{id}` `add`; the escalation rule applies). A role body
  takes catalog names only: a well-formed name that isn't in the catalog is 400 `bad_request`.
- No privilege escalation: a role's permissions can be added or removed, and a role can be given to or taken from a
  user, only by an actor who holds every permission involved (403 `forbidden`).
- A module's `view` comes with its other actions: a role that holds `user.create`, `user.edit` or `user.delete` also
  holds `user.view` (the same for `role.*` → `role.view`, `permission.create` → `permission.view`). `POST /api/roles`
  and `PATCH /api/roles/{id}` add it (and it counts for the escalation check); removing `view` while another action of
  the module stays leaves it on.
- Roles are referenced by name (users hold role names, like the source app). Names are unique ignoring letter case,
  and every lookup (`roles` in user bodies, the `role` filter, bulk `role`) ignores case and stores the role's own
  name. A rename (`PATCH /api/roles/{id}` with `name`, letter case included) moves every holder to the new name in the
  same step; a request that still sends the old name is 400 `bad_request` (unknown role).
- [PermissionDto](schemas/PermissionDto.json): `roles` lists at most 10 role names (A–Z), `roleCount` is how many
  roles hold the permission.
- `PATCH /api/users/{id}` checks every rule before changing anything. Changed fields (`name`, `username`, `email`,
  `roles`) write one `user.update` entry with only those fields; a status change writes `user.activate` /
  `user.deactivate`, the same rule and entry as `POST /api/users/{id}/status` and bulk activate / deactivate.
  Nothing to change → 200 with the user, no entry.
- Bulk `assignRole` skips a user who already holds 20 roles (the most one user holds) with `bad_request`.
- Actor rank: an actor may act on another user (`PATCH`/`DELETE /api/users/{id}`, `/status`, `/reset-password`,
  `DELETE /api/users/{id}/sessions/{sid}`, every bulk action) only when they hold every permission that user has
  (their effective permissions, the union of their roles). Otherwise 403 `forbidden`, checked after the 404 and before
  the other rules; bulk skips such a row with `forbidden`. So a `user.edit` holder can't reset, edit, deactivate,
  delete or sign out a Superadmin. The rows of `GET /api/users` and `GET /api/users/{id}` carry `permissions` so the
  screen can block those actions up front.
- Projects: names are unique ignoring letter case (409 `duplicate`); an empty `description` is stored as none
  (`null`). `PATCH /api/projects/{id}` writes one `project.update` entry with only the changed fields of `name`,
  `description`, `status`; nothing to change → 200 with the project, no entry.
- Spaces: a route under `/api/spaces/{spaceId}` checks the caller's roles in that space on every request (a removed
  member is 403 on the next one) and lets a non-member in only where its row names a global permission (`space.view` to read the space and its
  members, `space.manage` to change them): that gives no access to the space's data. A `spaceId` that is not a UUID is 404 before the roles are read, after the
  401. In an archived space a change on a data route (one whose row names no global permission) is 409 `space_archived`
  after the 403; reads and the space's own management rows (`PATCH /api/spaces/{spaceId}`, members) still work, so a
  space admin can reactivate it. `PUT …/members/{userId}` and `DELETE` re-read the caller's right to manage members inside the change, and refuse
  to leave a space without an active `space_admin` (409 `last_space_admin`, also for a PUT that drops the role; an
  inactive account's `space_admin` role does not count); two such changes run one after the other. Deleting or
  deactivating the only active `space_admin` of a space through `/api/users*` is 409 `last_space_admin` too, its message naming the space
  ("… of Treasury (treasury) …"; bulk skips that user with the code), under the same lock. Granting or removing `source_admin` (a PUT that adds or drops it, a DELETE of its
  holder) needs `space.manage`; a `space_admin` without it gets 403 `forbidden` (spec §11b). A code may be sent in any
  letter case (the schema shows the stored form); it is stored in lower case and unique. On fresh installs the default
  seed gives Admin `space.view` and `space.manage` (an existing deployment's Admin does not get `space.*`
  automatically), so an Admin can add themselves to any space (recorded as `space.member_set`; no second approval,
  spec §11b); taking that away is a one-line exception to Admin's permissions in `apps/api/src/db/seed/system.ts`.
- Sources: every route under `/api/spaces/{spaceId}/sources` takes a role in the space and names no global permission
  (a platform admin has no data access), so in an archived space each change is 409 `space_archived`. A source belongs
  to one space; `PUT …/shares/{toSpaceId}` lets another space read it and its published versions, never its draft or
  connection, and change nothing (row level security, `drizzle/0011_sources_rls.sql`): there it is listed with
  `shared: true`, and its change routes answer 404. The connection's host, port, database, user and password are stored
  encrypted and never logged or recorded; the PUT's answer and the entry carry `engine` and `options` only. The source's
  detail answers a source admin of the owner space also `connection.server` (host, port, database, user) so Change
  shows what is stored; the password is never answered. A
  version moves draft → in review (`submit`) → published (`approve`; the published one before it retires) or back to
  draft (`reject`, with a comment); a source has at most one draft or version in review (409 `duplicate` for a second).
  `makerId` is who last saved the spec (the draft's creator until then); `contributorIds` is everyone who created it,
  changed its spec or submitted it, kept through a reject and re-edit; any of them approving or rejecting it is 409
  `self_approval`; a step from the wrong status is 409 `invalid_state`. `spec` ([SourceSpec](schemas/SourceSpec.json))
  is checked across fields too (a name a mapping or key uses must be a field or derived value, field names unique, a
  mutable source has key fields, a watermark input names a table or a query, a snapshot query takes `:business_date`),
  its `input.kind` must be the source's kind and its `calendar` an existing calendar code (`id-default` on every
  install), else 400; `specHash` is SHA-256 of the spec as JSON with sorted keys, so the same spec saved again changes
  nothing. `POST …/connection/test`, `POST …/connection/catalog`, `GET …/connection/columns` and a database source's preview decrypt the stored
  credential on the server only and reach the source database within 8 s in all (the web gives up after 10 s); every
  failure is one fixed sentence per class (timeout, login refused, TLS not trusted, host unreachable, database not
  found, query refused) quoting the driver's code (`28P01`, `ER_ACCESS_DENIED_ERROR`, `ELOGIN`, `ORA-01017` …), never
  its text. A file inbox source's test reads the folder of the spec being worked on, which must be inside `INBOX_ROOTS`
  (also after symlinks are followed), else 400. A database test or catalog list typed with no database connects to the
  engine's default (PostgreSQL `postgres`, SQL Server `master`, MySQL none; Oracle needs its service name); a passing
  test says what it found ("Connected to PostgreSQL 18.6 as recon_ro. 3 databases; 128 tables in recon_core.", a
  number not read within the deadline left out). Catalog lists send only fixed per-dialect SQL with bound values and
  list only what the login may open or SELECT.
- Recons: every route under `/api/spaces/{spaceId}/recons` takes a role in the space and names no global permission, so
  in an archived space each change is 409 `space_archived`. A recon has exactly two sides, each reading a source of the
  space or one shared to it (DEC-042; another space's unshared source is 400). Its versions move as a source's do
  (draft → in review → published, or back with a comment; `contributorIds` may not check it, 409 `self_approval`).
  The spec is checked against each side's published source version: a field it names must be one those records have
  (a core field the version maps, or a stored attribute; a matching key or condition names one field for both sides, or
  `{ "a": …, "b": … }`, each side's own) and of the kind its condition compares; passes are numbered
  1, 2, 3 …; a group sum only in a 1:N or N:1 pass, which needs a matching key; an amount compared where the sides can
  hold more than one currency needs a currency condition. A tolerance is per currency in major units (`{ "IDR":
  "1000.00" }`, no more decimal places than the currency's ISO 4217 minor unit). Messages name the spot as the builder
  does ("Pass 2, condition 1"), never a spec path. Submit needs `simulatedHash` equal to `specHash` (the last
  simulation ran on the spec as it is). Publishing records which fields of each source the recon reads, and a source
  version that drops or retypes one is then refused at submit and approve (`drizzle/0021_recon_rls.sql`: the source's
  space reads those rows, never the recon).
- Runs: `POST …/recons/{configId}/runs` and `POST …/versions/{versionId}/simulate` answer 202 with the run, status
  `queued`, pinned to its version; the worker runs it (queue `recon.heavy`) and the screen polls `GET …/runs/{runId}`
  (`queued` → `running` → `succeeded` | `failed` with `error` in a sentence). One run of a recon at a time: a request
  while another is queued or running is 409 `invalid_state` ("This recon is already running. Wait for that run to
  finish, then start another."); a run whose job ended without it is failed then ("The run stopped before it finished.
  Run it again."). A simulation also runs the published version over the same business dates and lists the pairs that
  change (`GET …/runs/{runId}/changes`: gained, lost, re-paired, auto ↔ suggested); when it succeeds on the draft as it
  still is, the draft's `simulatedHash` = its `specHash` (submit opens; an edit closes it again). Only the latest
  simulation of a version is kept, with its changes.
- Scheduled runs (no route): a minute job (queue `recon.schedule`) starts `tick` runs of an interval recon (queue
  `recon.tick`) and `daily` runs of a daily one (`recon.daily`) through the same one-run-at-a-time check, from the day
  after the last closed business date (a worker that was down catches up); a recon whose last scheduled run failed waits
  15 minutes (or its interval). A run's live items past grace break; after a date's close moment its open items and
  unconfirmed suggestions become breaks (day close, `recon_days`), once the run's intake saw every side complete through
  the date's end, or at close + grace marked incomplete. With carry over > 0 a "No counterpart" break (no other reason) stays a
  candidate of every pass of later runs (DEC-047): an automatic pass closes it as `AUTO_MATCHED_LATE_DATA`, a suggesting
  pass leaves it a break with the pair proposed. Those runs list in `GET …/runs` with their mode.
- Every POST/PATCH/PUT/DELETE outside `/api/auth/*` that changes something writes an activity entry; sign-in, sign-out
  and 2FA steps write sign-in log entries. `POST /api/me/reauth` is an auth step and writes neither.

### Activity log entries

`GET /api/audit/activity/{id}` reads one retained immutable entry using `audit.view`, independently of list filters,
range or page. The guard runs before UUID parsing/read; an invalid UUID, missing entry or retained-history purge is
404. Actor/target records need not still exist. The response is the existing ActivityDto, with recorded identities
and masked snapshots; no extra target lookup or auth-log endpoint is implied.

Activity list/count/CSV accept exact `actorId` (case-insensitive UUID shape) and paired `targetType` (1–64 characters)
plus `targetId` (1–512 characters). Target strings are opaque: no trimming, case folding or substring matching.
U+0000 is rejected because PostgreSQL text cannot store it; other controls/whitespace remain exact recorded values.
They combine with existing action/user/time filters using AND. Both target keys are required together; invalid/empty/
overlength values are400 before authentication. Repeated scalar keys use the first value. Longer historical target
IDs remain available in entry detail; an exact URL filter is not offered for them. No migration/index change is needed
for this contract: existing actor and target indexes are retained.

Each entry: `{ id, at, actor: { id, name }, action, target: { type, id, label }, before, after }`
([ActivityDto](schemas/ActivityDto.json)). `before` / `after` are plain-data snapshots taken when the entry is written
(later edits don't change history) and are `null` when the action has none. Masking: a record's own credential fields
(`passwordHash`, `totpSecret`, `pendingTotpSecret`, `recoveryCodes`) are dropped, and any other field whose name
matches `password|secret|token|recovery` (any letter case, at any depth) keeps only `"••••"` when it had a value
(`HIDDEN` and `SECRET_KEY` in `apps/api/src/modules/audit/rules.ts` and `packages/shared/src/audit.ts`). The table below is
generated from the action vocabulary (`ACTION_LABEL` in `packages/shared/src/audit.ts`) by `bun run api:schemas`;
`api-contract.test.ts` fails when it drifts.

The activity detail and CSV `Changes` cell share the action-aware presentation in
`packages/shared/src/audit-changes.ts`. Known creates show initial values; deletes show values before deletion.
Only complete recorded role/permission sets produce added/removed differences (reordering alone is ignored).
Explicit role permission deltas and permission registration lists are shown as recorded; malformed or unknown shapes
fall back to masked values/JSON. Missing fields, null, empty text and empty arrays remain distinct. Unknown arrays
retain item boundaries/order, and identical masked credentials never imply a changed secret. This changes presentation
only: the stored snapshots, JSON DTO, CSV column order, filters and formula-safe encoding are unchanged.

### Backend notes

- Each area is a module of `apps/api/src/modules/` (controller, service, Drizzle schema, pure rules) that owns its
  tables; every query goes through Drizzle's builder, migrations are drizzle-kit output plus custom SQL in
  `apps/api/drizzle/`. The rules for adding to it are `AGENTS.md` §12 and §13.
- A change and its activity entry commit in one transaction. Rules two requests could both pass (the last active
  Superadmin, the 500-name catalog) are checked under a PostgreSQL advisory lock, and the actor's permissions and the
  target's rank are read inside the transaction after the row lock.
- Every connection runs with a 5 s statement timeout; lists count at most 100,000 rows (`totalCapped` beyond).
- Users list: `q` searches name, username and email with a substring match (`ILIKE`, served by trigram GIN indexes,
  `apps/api/drizzle/0001_custom.sql`). `GET /api/users/{id}` reads the last 20 entries targeting the user (index
  `activity (target_id, at DESC)`). `RoleDto.userCount` is a `GROUP BY role` count over the user–role table, not a
  per-role query.
- Recovery codes: 8 codes of 80 random bits each, stored as Argon2id hashes, spent on use.
- Google/Apple sign-in and linking: the state is stored hashed and is valid once for 10 minutes. It is bound to the
  browser by the `sk_oauth` cookie and to the browser's session when there is one: ending that session (sign-out,
  revoke) cancels the round trip, and a sign-in through the provider ends it. A link needs that session to be live at
  the callback. A second start in another tab replaces the first (one `sk_oauth` per browser). Starts: 20 per minute
  per client IP, 300 in all.
- Reset and invitation links: 32 random bytes (base64url), stored only as a SHA-256 hash, one live link per user
  (a new one replaces the old), single use (spent even when expired), valid 30 minutes (reset) or 72 hours
  (invitation). They are spent by a password change, an admin reset, a deactivation, an email change (admin or own) and
  deleting the user. A reset by link ends all of the user's sessions; an inactive user's link is refused
  (`invalid_code`, spent).

## Seed data

`bun run db:seed` (`apps/api/src/db/seed/system.ts`) writes the permission catalog, the roles Superadmin (every
permission, locked), Admin (all but `role.*` and `permission.*`) and Viewer (`user.view`, `audit.view`), and the
Superadmin named by `SEED_SUPERADMIN_*`. `bun run db:seed:demo` (`apps/api/src/db/seed/demo.ts`, refused in production)
adds the demo users, activity and sign-in log entries; the sign-in accounts are listed in the root README.
`bun run db:reset` drops the schema, migrates and runs both.
